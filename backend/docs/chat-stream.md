# Chat stream contract

`POST /v1/chat/stream` runs one chat turn and streams it as Server-Sent Events. Phase 5 pipes it unchanged through `/api/chat`; Phase 7's assistant-ui `ChatModelAdapter` consumes it. This file is the contract: if the code and this file disagree, fix the file or the code, not the adapter.

Examples below are copied from a real run against the live model (`gpt-6-luna`, default tier) unless marked **(test suite)**. Long strings are shortened with `…`.

## Request

```
POST /v1/chat/stream
X-Internal-Key: <INTERNAL_API_KEY>
X-User-Id: <Better Auth user id>
Content-Type: application/json

{ "session_id": "f32759b6-1536-4f65-aa79-234efb439ed6",
  "message": "Which law governs the agreement?",
  "document_ids": ["b81a691c-…"] }          // optional
```

| Field | Rules |
|---|---|
| `session_id` | UUID, **generated by the client** (`crypto.randomUUID()`). The session is created on the first message. Sending another user's session id is a `404`. |
| `message` | 1 to 8000 characters after trimming. |
| `document_ids` | Optional. **Omitted:** keep the session's selection (a new session starts with all documents). **A list:** set the selection (every id must be the caller's, else `404`). **`[]` or `null`:** clear it, i.e. chat over all documents. |

The history (last `HISTORY_WINDOW` = 20 messages) is loaded server-side. The client never sends it.

### Errors before the stream starts (plain JSON, not SSE)

Body shape is the usual `{success:false, status, message, details}`.

| HTTP | `status` | When |
|---|---|---|
| 402 | `INSUFFICIENT_CREDITS` | Message balance is 0. Nothing is stored, nothing is charged. |
| 404 | `NOT_FOUND` | Session belongs to someone else, or a `document_ids` entry is not the caller's. |
| 422 | `VALIDATION_ERROR` | Bad body (missing `session_id`, blank message, ...). |
| 401 | `UNAUTHORIZED` | Missing or wrong `X-Internal-Key` / `X-User-Id`. |

Otherwise the response is `200` with `Content-Type: text/event-stream`, `Cache-Control: no-cache, no-transform` and `X-Accel-Buffering: no`. One credit has been reserved at this point.

## Wire format

Standard SSE. Each event is two lines and a blank line: `event: <name>` then `data: <one line of JSON>`. There are no comments, ids or retry fields. The `data` payload is always a JSON object. All timestamps are ISO 8601 UTC.

## Events

Order for a normal turn:

```
message.start
  ( reasoning.delta* | tool.start tool.end | text.delta* )*      # interleaved as the agent works
citation*                                                        # after the answer text is complete
message.end                                                      # always the terminal event of the run
session.title                                                    # only after the first completed turn
```

On failure the order is `... error message.end` (see `error`). If the client disconnects, the server stops; nothing more is sent.

### `message.start`

First event. The ids the UI needs for the new pair of messages.

```
event: message.start
data: {"session_id": "f32759b6-1536-4f65-aa79-234efb439ed6", "user_message_id": "26fbe149-265e-4fa4-8004-ed391c3b550d", "message_id": "352b0acb-48b7-405b-ba97-5da6db9e7c36", "created_at": "2026-11-11T19:13:00.766704+00:00"}
```

`message_id` is the **assistant** message id. Use it for feedback (`PUT /v1/messages/{message_id}/feedback`) once the stream ends.

### `reasoning.delta`

A chunk of the model's reasoning **summary**, as Markdown (it usually starts with a bold heading such as `**Evaluating revenue interpretation**`, and separate summary sections are separated by a blank line). Concatenate the deltas.

```
event: reasoning.delta
data: {"text": " interpret"}
```

It is **optional**: the model decides whether to reason, and for easy questions a turn has no `reasoning.delta` at all (`metrics.reasoning_tokens` is then 0 or the summary is simply empty). Reasoning may appear before, between or after tool calls.

### `tool.start`

A tool call is about to run (emitted once its arguments are complete).

```
event: tool.start
data: {"id": "call_hg89FVtA7Adb07ICBmHsGQLA", "name": "search_documents", "args": {"query": "agreement governing law choice of law jurisdiction invoice payment due date", "document_id": ""}}
```

`name` is one of `list_documents`, `search_documents`, `get_document_text`, `query_table`. `args` is the parsed JSON object the model sent (the model may send empty strings for optional arguments, as above). `id` pairs a start with its end.

### `tool.end`

```
event: tool.end
data: {"id": "call_hg89FVtA7Adb07ICBmHsGQLA", "name": "search_documents", "ok": true, "summary": "1 passages from 1 document", "duration_ms": 5042}
```

`summary` is a short human-readable result line ("2 documents", "3 rows", "report.pdf: 12,430 characters (truncated)", or `Error: ...` when `ok` is false). The raw tool output is deliberately **not** streamed. `ok: false` means the tool refused or failed (for example the SQL guard rejected a query); the model sees the error and usually retries, so a failed tool call is not a failed turn. Tools run one at a time, in order.

### `text.delta`

A chunk of the answer, as Markdown. Concatenate in order.

```
event: text.delta
data: {"text": " agreement"}
```

The text contains citation markers like `[1]` or `[1][3]` (see `citation`). Render them as links to the matching `citation` event, or strip them when no citation matches.

### `citation`

One event per source the answer **actually cites** (a `[n]` marker appears in the text), ascending by `index`, sent after the last `text.delta`. Numbers restart at 1 on every turn.

```
event: citation
data: {"index": 1, "document_id": "b81a691c-88a5-4892-ab28-0d23c6a712cc", "file_name": "contract.pdf", "page_start": 1, "page_end": 2, "snippet": "SERVICES AGREEMENT 1. Payment. The client shall pay each invoice within 30 days of receipt. 2. Confidentiality. …"}
```

| Field | Notes |
|---|---|
| `index` | The number the answer text uses (`[1]`). |
| `document_id`, `file_name` | The cited document. Open it in the viewer with `GET /v1/documents/{id}/content`. |
| `page_start`, `page_end` | Page range of the cited **chunk** (about 1000 characters, so it can span pages). `null` for CSV tables. For DOCX and TXT the pages are approximate (see Phase 2). |
| `snippet` | First ~240 characters of the passage, whitespace-collapsed. For a CSV answer it is the SQL that was run: `"SQL: SELECT region, SUM(revenue) … FROM rows …"`. For `get_document_text` it is the start of the document. |

### `error`

Something went wrong inside the run. It is always followed by `message.end`. **(test suite)**

```
event: error
data: {"code": "LLM_BUSY", "message": "The model is busy right now. Please try again in a moment."}
```

| `code` | Meaning |
|---|---|
| `LLM_BUSY` | The provider rate-limited or the flex tier had no capacity (and the fallback tier failed too). Retryable. |
| `LLM_TIMEOUT` | The model call timed out. Retryable. |
| `LLM_ERROR` | The model call failed or returned no answer. Retryable. |
| `INTERNAL_ERROR` | A bug on our side. The message is generic; details are only in the server log. |

`INSUFFICIENT_CREDITS` never appears in the stream: it is the HTTP 402 above. Provider error text is never forwarded. If some answer text was already streamed, the message is kept as `incomplete`; if none was, the credit is refunded and the message is stored as `error`.

### `message.end`

Terminal event of the run. Persistence has already happened when it is sent, so the client may refetch immediately.

```
event: message.end
data: {"message_id": "352b0acb-48b7-405b-ba97-5da6db9e7c36", "status": "complete", "usage": {"input_tokens": 2405, "output_tokens": 113, "reasoning_tokens": 26, "cached_tokens": 2201}, "metrics": {"ttft_ms": 9505, "total_ms": 11299, "output_tokens": 113, "input_tokens": 2405, "reasoning_tokens": 26, "tokens_per_s": 23.8, "steps": 2, "tool_calls": 1, "model": "gpt-6-luna", "service_tier": "default", "flex_fallback": false}}
```

`status` is `complete`, `incomplete` (cut short after some text) or `error` (nothing produced; credit refunded).

`usage` is the token total across every model call in the turn (query-embedding tokens are not included).

`metrics` (identical to what `GET /v1/sessions/{id}/messages` returns later):

| Field | Definition |
|---|---|
| `ttft_ms` | Server-side time from the start of the run (after the credit and user message were stored) to the **first answer `text.delta`**. Includes reasoning and tool time. `null` if no answer text was produced. |
| `total_ms` | Same start to the end of the run. |
| `output_tokens` | Output tokens of all model calls (reasoning tokens included, as the API counts them). |
| `tokens_per_s` | `output_tokens` divided by the time spent **streaming from the model** (tool execution excluded). `null` if there were no output tokens. |
| `input_tokens`, `reasoning_tokens` | Totals across model calls. |
| `steps` | Number of model calls (the agent loop is capped at `AGENT_MAX_STEPS`). |
| `tool_calls` | Number of tool calls. |
| `model`, `service_tier` | Model used and the tier that actually served it. |
| `flex_fallback` | `true` if flex was requested, was unavailable, and the run was retried on `FLEX_FALLBACK_TIER`. |

### `session.title`

Sent **after** `message.end`, and only after the first completed turn of a session (title was still empty). The stream closes right after. It can lag `message.end` by 1 to 3 seconds (one small extra model call), so do not hold the UI on it.

```
event: session.title
data: {"session_id": "f32759b6-1536-4f65-aa79-234efb439ed6", "title": "Governing Law and Invoice Payment Deadline"}
```

If title generation fails the title falls back to the start of the user's message. If the client has already disconnected, no title is generated; the next completed turn gets one.

## Disconnects and credits

- **One credit is reserved before streaming** and the user message is stored. If the client disconnects, the model call is cancelled and the partial assistant message is stored as `incomplete` (what was streamed so far, plus a `citation` part for any marker already in the text).
- **Refund rule:** if the run ends with no answer text (error, empty answer, or disconnect before any text), the credit is refunded and the ledger shows a `usage` row followed by a `refund` row. If any answer text was produced, the credit stays spent.
- After any stream, refresh credits (`refreshAll()`).

## How a turn is stored

`GET /v1/sessions/{session_id}/messages` returns, per message:

```
{ "id", "role": "user" | "assistant", "content", "parts", "metrics",
  "status": "complete" | "incomplete" | "error", "model", "created_at",
  "feedback": null | {"message_id", "rating": "like"|"dislike", "reason", "comment"} }
```

User messages have `parts: null` and `metrics: null`. For assistant messages `content` is the concatenated answer text and `parts` is the ordered list of what happened, in stream order. Consecutive reasoning chunks and consecutive text chunks are merged:

```
[
  {"type": "reasoning", "text": "**Evaluating revenue interpretation**\n\nI need to …"},
  {"type": "tool", "id": "call_hg89…", "name": "search_documents",
   "args": {"query": "…", "document_id": ""},
   "status": "done" | "error", "result_summary": "1 passages from 1 document", "duration_ms": 5042},
  {"type": "text", "text": "The agreement is governed by the laws of **Ireland**. … [1]"},
  {"type": "citation", "index": 1, "document_id": "b81a691c-…", "file_name": "contract.pdf",
   "page_start": 1, "page_end": 2, "snippet": "SERVICES AGREEMENT 1. Payment. …"},
  {"type": "error", "code": "LLM_ERROR", "message": "…"}      // only on failed / incomplete turns
]
```

`parts` is exactly what the stream showed, so one renderer can serve both live and reloaded messages. A tool that was still running when the run was cut short is stored with `status: "error"`.

## What the agent can do

| Tool | Reads | Notes |
|---|---|---|
| `list_documents` | the user's `ready` documents (respecting the chat's selection) | includes CSV column names and types |
| `search_documents` | hybrid search (semantic + keyword, fused with RRF), top 8 chunks | each result is numbered `[n]` for citation |
| `get_document_text` | one document's full text, overlap removed, with `[Page N]` markers | truncated at about 25,000 tokens |
| `query_table` | one SQL `SELECT` over one CSV, as a table named `rows` | single `SELECT` only (no `WITH`/`UNION`), allowlisted functions, 100 rows max, 5 s timeout, read-only |

All of them are scoped to the caller's own documents and, when set, the chat's selection.
